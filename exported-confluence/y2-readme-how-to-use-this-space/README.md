# 0. Y2 README - How to use this space

# Channel Strategy Y2 Space

## Purpose of this space

This Confluence space is the source of truth for Channel Strategy Y2.

It explains what the project is doing, how the work is organised, where documentation lives, how decisions are recorded, and how Confluence and Jira work together.

The space is designed around the 4D delivery cycle:

- Discover
- Define
- Design
- Deliver

Each major deliverable has its own parent page, with child pages for each stage of the 4D cycle.

---

## Simple rule

**Confluence explains the work. Jira manages the work.**

Confluence is where we document the project, its logic, decisions, artefacts and source-of-truth material.

Jira is where we manage delivery activity, track progress, assign work and manage sprints.

## Why this structure

This structure keeps the space clear and scalable.

Each deliverable has one parent page that acts as the control page for that body of work.

Each 4D child page captures the detail for that stage.

This avoids having many disconnected pages and makes it easier for people to understand:

- what each deliverable is trying to achieve
- what stage the work is in
- what has been learned
- what has been decided
- what needs to happen next
- where Jira delivery work is being tracked

---

## Deliverable parent pages

Each Confluence deliverable parent page acts as the control page for that deliverable.

It should not duplicate all the content from the 4D child pages.

It should summarise the work and link to the detail.

Each deliverable parent page should include:

| Section | Purpose |
| --- | --- |
| Purpose | What this deliverable is about |
| Current stage | Which 4D stage the work is currently in |
| Owner | Who owns the deliverable |
| Related Jira deliverables | Links to the relevant Jira 4D deliverable cards, where created |
| Summary | Short plain-English explanation |
| Key outputs | What this deliverable will produce |
| 4D page links | Links to Discover, Define, Design and Deliver child pages |
| Key decisions | Important decisions affecting this deliverable |
| Open questions | Questions that still need resolution |
| Risks and dependencies | Key items linked to the risk register or RAID |
| Latest status | Brief update on progress |

**Important:** Do not use the Confluence parent page to duplicate Jira task detail. Jira tracks active delivery work. Confluence explains the purpose, logic, evidence and decisions.

## Jira board and automation

The Channel Strategy Y2 shared sprint board is used by the Customer Focus Team and Contact Centre Team to manage shared delivery work.

### Board purpose

The board is used to:

- show active Channel Strategy Y2 work
- support shared sprint planning
- make ownership and progress visible
- avoid duplicating project documentation in Jira

### Board inclusion rule

Channel Strategy Y2 work items use the label:

**channel-strategy-y2**

The shared sprint board displays work that belongs to Channel Strategy Y2.

### Automation rule

When a new work item is created, if its parent already has the label **channel-strategy-y2**, Jira automatically adds the same label to the new child work item.

This means the label flows through the hierarchy:

Initiative

- Deliverable

  - Epic

    - User Story / Task

      - Sub-task

### Why this matters

This automation means:

- new work items appear on the shared board automatically
- teams do not need to remember to add the label manually
- the rule remains sustainable as new deliverables are added
- the board does not need to be manually updated every time the structure grows

### Important

If a work item is created outside the Channel Strategy Y2 hierarchy, it may not appear on the board unless it has the **channel-strategy-y2** label.

| Jira Initiative | Confluence project page | Provides project context and source-of-truth material |
| Jira Deliverable | Relevant Confluence 4D page | Provides phase context and documentation |
| Jira Epic | Relevant Confluence 4D page or section | Provides work package context |
| Jira Story or Task | Specific Confluence section or page | Helps the assignee understand the work |
| Decision Log | Relevant Jira deliverable, epic, story or task | Shows what delivery work is affected by a decision |

### Linking rules

- Confluence explains the work.
- Jira manages the work.
- Use links rather than copying large amounts of content between tools.
- Do not use Jira comments as the only record of an important decision.

## Artefacts

An **artefact** is a reusable project output that helps explain, decide, design, validate or apply the work.

Artefacts remain within the relevant deliverable and 4D stage. Do not create a separate page hierarchy simply because something is an artefact.

Examples include:

- frameworks
- models
- current-state or future-state maps
- analysis outputs that provide reusable evidence
- design patterns
- decision aids
- templates
- reusable reference material

Examples of content that is **not normally an artefact** include:

- meeting notes
- sprint updates
- Jira task descriptions
- RAID entries
- working comments
- temporary analysis
- intermediate drafts that have no ongoing reuse value

### Artefact metadata

Where `Artefact = Yes`, use one of the following controlled artefact types:

| Artefact type | Use |
| --- | --- |
| **Framework** | Organising logic, principles or decision structure used across multiple situations |
| **Model** | Structured representation of concepts, relationships or classifications |
| **Map** | Visual or structured representation of journeys, systems, flows, relationships or current/future state |
| **Analysis** | Evidence-based analysis intended to inform more than the task that created it |
| **Pattern** | Reusable service, interaction, content or design solution |
| **Decision aid** | Tool or criteria that supports a defined decision |
| **Template** | Repeatable structure for producing consistent outputs |
| **Reference** | Stable reference material intended for repeated use |

Use the closest existing type. Do not create a new artefact type for isolated cases.

### Artefact lifecycle

Artefact status uses the normal page-status convention:

- **Draft** — still being shaped or validated
- **In review** — ready for stakeholder feedback
- **Endorsed** — agreed for current project use
- **Superseded** — replaced by a newer artefact
- **Archived** — retained for reference only

Artefacts may evolve across the 4D cycle.

For example:

**Discover**  
→ current-state map

**Define**  
→ agreed principles or decision framework

**Design**  
→ future-state model or pattern

**Deliver**  
→ tested or embedded version

Where an artefact evolves, link related versions rather than duplicating content without explanation.

### Artefact rule

**Pages are organised by deliverable and 4D stage. Artefact metadata identifies reusable outputs within that structure.**

A future Library or index may surface artefacts across the project if this becomes useful. The Library should link to source pages rather than duplicate their content.

## Working principles

### 1. One source of truth

If something is important and enduring, it belongs in Confluence.

If something is delivery activity, it belongs in Jira.

### 2. Parent pages summarise, child pages hold detail

Deliverable parent pages should provide orientation and links.

The 4D child pages should hold detailed stage content.

### 3. Do not create duplicate documentation

Avoid copying the same content into Jira, Confluence and other tools.

Use links instead.

### 4. Document decisions, not every conversation

Confluence should capture decisions, rationale, assumptions, risks, dependencies and reusable artefacts.

It does not need to capture every discussion.

### 5. Keep Jira practical

Jira should make delivery visible without becoming a second documentation system.

For Channel Strategy Y2:

- Deliverables are phase-level containers
- Epics group related work
- User Stories and Tasks are the visible sprint cards
- Sub-tasks are optional and should be used sparingly

### 6. Make progress visible

A stakeholder should be able to understand the work by looking at:

- the project landing page
- the deliverable parent pages
- the relevant 4D child pages
- the decision log
- the risk register
- the Jira board

---

## What not to do

Avoid the following:

- using Jira comments as the only record of an important decision
- creating Confluence pages with no owner
- duplicating the same content in Confluence and Jira
- using Jira to explain the full project background
- using Confluence to manage every subtask
- leaving outdated pages without a status
- creating new documentation locations without explaining why
- treating the README as the place for all templates and working artefacts
- creating Jira placeholders for phases that are not yet active
- relying on manual labelling when the item should inherit the **channel-strategy-y2** label from its parent
