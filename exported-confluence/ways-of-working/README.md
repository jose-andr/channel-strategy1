## Purpose

This page defines how Channel Strategy Y2 will work with related teams, initiatives and governance groups.

Channel Strategy Y2 will not own every channel improvement across City of Melbourne. Instead, it will provide the practical **customer experience enablement layer** that helps related work stay aligned to connected customer interactions.

The role of the project team will shift depending on the situation. Sometimes we will act as **advisors**, sometimes as **collaborators**, sometimes as **enablers**, and sometimes as a lightweight **oversight / assurance** function.

The aim is to support better outcomes without becoming a bottleneck.

## Working model summary

| Mode | What it means | When to use it | Level of involvement |
| --- | --- | --- | --- |
| **Advisor** | We provide guidance, challenge, review and recommendations | Another team owns delivery but needs channel / CX input | Light |
| **Collaborator** | We co-design part of the work with another team | The work directly affects connected interactions, customer journeys or channel decisions | Medium |
| **Enabler** | We create reusable tools, patterns and standards for others to apply | Multiple teams need a common approach | Medium |
| **Oversight / assurance** | We maintain visibility and check alignment across related initiatives | Work may affect channel strategy outcomes, customer experience consistency or cross-channel architecture | Light to medium |
| **Owner** | We directly own and deliver the artefact or decision | The output is core to Channel Strategy Y2 | High |

## Core principle

Channel Strategy Y2 should **shape and enable connected customer interactions**, not become the default delivery owner for every channel-related initiative.

This means:

| We should do | We should avoid |
| --- | --- |
| Create reusable patterns and standards | Becoming the delivery team for all channel fixes |
| Help teams make better channel decisions | Reviewing every small operational change |
| Provide early design input | Being brought in only at final approval |
| Maintain visibility across related initiatives | Creating heavy governance or duplicated reporting |
| Focus on high-value journeys and decisions | Spreading effort thinly across too many activities |
| Help teams align to shared service logic | Letting each channel optimise in isolation |

## Role of Channel Strategy Y2

Channel Strategy Y2 plays five roles across the portfolio of related work.

| Role | Description | Example activities |
| --- | --- | --- |
| **Strategic framer** | Clarifies the customer and channel logic that should guide decisions | Define response modes, routing principles and connected interaction standards |
| **Advisor** | Provides targeted advice to related projects | Review a digital pathway, challenge a channel assumption, advise on customer status language |
| **Collaborator** | Works with another team to co-design a shared output | Co-design front-door routing logic with Digital and service owners |
| **Enabler** | Produces tools others can use without needing ongoing support | Templates, decision trees, journey patterns, status pattern library |
| **Assurance partner** | Checks whether related work aligns to the Connected Interactions Framework | Lightweight review of project artefacts at key points |

## Engagement modes

### 1. Advisor mode

Use **Advisor mode** when another team owns the work and only needs targeted CX / channel strategy guidance.

| Element | Description |
| --- | --- |
| Purpose | Help another team make a better decision without taking over delivery |
| Typical effort | 1–3 sessions or a short review |
| Ownership | Delivery team owns outcomes and implementation |
| Channel Strategy Y2 contribution | Advice, review, challenge, principles, examples |
| Output | Written comments, recommendation, design review notes or decision input |

#### Advisor mode examples

| Example | Channel Strategy Y2 contribution |
| --- | --- |
| A team is updating web content for a high-demand service | Advise on intent-led language and pathway clarity |
| CRM team is changing status labels | Advise on customer-facing status principles |
| Contact centre is reviewing scripts | Advise on response modes and handover context |
| Digital Assistant work needs service logic input | Advise on source-of-truth, routing and escalation pathways |

#### Advisor mode entry criteria

Use Advisor mode when:

1. the work has a clear owner outside Channel Strategy Y2
2. the decision affects customer channel experience
3. the request can be answered through existing principles or light review
4. no major co-design or new artefact is required

### 2. Collaborator mode

Use **Collaborator mode** when Channel Strategy Y2 needs to actively co-design part of the work with another team.

| Element | Description |
| --- | --- |
| Purpose | Co-create a shared artefact, decision or test |
| Typical effort | Time-boxed sprint, workshop series or defined work package |
| Ownership | Shared for the specific output; delivery ownership remains agreed upfront |
| Channel Strategy Y2 contribution | Facilitation, journey logic, response modes, service design, decision tools |
| Output | Co-designed artefact, tested pattern, journey map, decision tree, prototype or recommendation |

#### Collaborator mode examples

| Example | Channel Strategy Y2 contribution |
| --- | --- |
| Intelligent Front Door Discovery | Co-design customer intent, support modes and routing logic |
| Information Architecture Discovery | Co-design service naming, support reasons and pathway structures |
| Customer status update work | Co-design status patterns with CRM, Comms and service teams |
| MVP journey test | Co-design the before / after experience and measurement approach |

#### Collaborator mode entry criteria

Use Collaborator mode when:

1. the work directly tests or shapes the Connected Interactions Framework
2. the outcome affects multiple channels or teams
3. the work needs CX / service design facilitation
4. the output is reusable across more than one service
5. the project lead confirms capacity and priority

### 3. Enabler mode

Use **Enabler mode** when Channel Strategy Y2 creates reusable assets that other teams can apply.

| Element | Description |
| --- | --- |
| Purpose | Help teams move faster and make consistent decisions |
| Typical effort | Create once, refine through use, maintain lightly |
| Ownership | Channel Strategy Y2 owns the enabling asset until ownership is transitioned |
| Channel Strategy Y2 contribution | Frameworks, standards, patterns, templates and examples |
| Output | Reusable artefact or toolkit |

#### Enabler assets

| Asset | Purpose | Primary users |
| --- | --- | --- |
| Connected Interactions Framework | Shared model for designing connected customer interactions | CX, Digital, CRM, Contact Centre, service owners |
| Response mode guide | Helps teams choose the right level of support and channel behaviour | Service owners, Contact Centre, Digital, CRM |
| Routing decision tree | Helps teams route customers to the right pathway | Digital, IVR, Digital Assistant, service owners |
| Customer status pattern library | Helps teams write meaningful updates in customer language | CRM, Comms, service teams |
| Minimum connected-context checklist | Defines what staff need to know at handover | CRM, Contact Centre, service teams |
| Journey measurement guide | Supports journey-based performance measurement | VOCA, analytics, service owners |
| Service information architecture principles | Helps organise services and support reasons by customer intent | Digital, Knowledge, IA, service teams |

#### Enabler mode entry criteria

Use Enabler mode when:

1. several teams need the same decision support
2. the pattern can be reused across services
3. the issue is likely to recur
4. the artefact reduces future advisory effort
5. the output can be tested through an active initiative

### 4. Oversight / assurance mode

Use **Oversight / assurance mode** when Channel Strategy Y2 needs visibility of related projects but does not need to be involved in all delivery detail.

| Element | Description |
| --- | --- |
| Purpose | Maintain alignment across related work and reduce channel drift |
| Typical effort | Lightweight check-ins, artefact review or portfolio scan |
| Ownership | Delivery teams own their projects; Channel Strategy Y2 tracks alignment |
| Channel Strategy Y2 contribution | Alignment checks, risk identification, dependency visibility, escalation advice |
| Output | Portfolio view, alignment notes, risks, decisions or recommendations |

#### Oversight / assurance focus areas

| Focus area | What we check |
| --- | --- |
| Customer intent | Is the work organised around what customers are trying to do? |
| Channel orchestration | Does it help channels work together, or just improve one channel? |
| Response mode alignment | Is the level of support appropriate to customer need, risk and complexity? |
| Handover | Will staff have enough context if the customer moves channel or team? |
| Knowledge | Is there a clear source of truth? |
| Status updates | Will customers understand what has happened and what happens next? |
| Measurement | Can the work be measured as part of a journey, not only as channel activity? |
| Accessibility and equity | Are assisted, accessible and language options protected? |
| Compliance | Are privacy, records, security and data governance considerations visible? |

#### Oversight / assurance entry criteria

Use Oversight / assurance mode when:

1. the work is channel-related but owned elsewhere
2. the work may affect customer experience consistency
3. the work has dependencies with other channel initiatives
4. the work could create duplication, conflicting language or fragmented journeys
5. the work may need future scale or executive visibility

## Engagement triage

Use this triage table when a team asks for Channel Strategy Y2 involvement.

| Question | If yes | Suggested mode |
| --- | --- | --- |
| Is the request about a core Y2 artefact or decision? | Channel Strategy Y2 should own it | Owner |
| Does the work directly test the Connected Interactions Framework? | Co-design is likely needed | Collaborator |
| Does the team need guidance but owns delivery? | Provide targeted input | Advisor |
| Is the same issue likely to appear across multiple services? | Create a reusable tool or pattern | Enabler |
| Does the work affect channel consistency but not require direct delivery support? | Track and review lightly | Oversight / assurance |
| Is the request outside the Y2 scope or too broad? | Record, redirect or defer | Not in scope / backlog |

All requests for support should be assessed before effort is committed.

| Step | Action | Owner | Output |
| --- | --- | --- | --- |
| 1. Capture | Record the request, project, owner and decision needed | Project lead | Intake item |
| 2. Triage | Assess against engagement modes | Project lead | Advisor / Collaborator / Enabler / Oversight / Owner / Defer |
| 3. Prioritise | Check value, urgency, capacity and Y2 alignment | Project lead with sponsor if needed | Priority rating |
| 4. Confirm role | Agree what Channel Strategy Y2 will and will not do | Project lead and requesting team | Clear engagement agreement |

| 6. Close or monitor | Close item or move to oversight view | Project lead | Updated log |

## Intake assessment criteria

| Criteria | High priority | Lower priority |
| --- | --- | --- |
| Customer impact | High-demand, high-effort or high-risk journey | Low-volume or low-impact change |
| Strategic alignment | Directly supports connected interactions | General service improvement only |

| Risk | Privacy, equity, reputation or service risk is material | Low risk |

## Working agreements

| Agreement | What it means |
| --- | --- |
| We start with the customer journey | Discussions should begin with customer intent, effort and outcome |
| We make the role clear upfront | Every engagement should state whether we are advising, collaborating, enabling, overseeing or owning |
| We time-box support | Advisory and collaboration support should have a clear start, end and output |
| We use shared language | Response modes, routing, status, knowledge and IA terms should be consistent |
| We document decisions | Material decisions go in the Decision Log |
| We keep artefacts reusable | Outputs should be useful beyond a single meeting or project where possible |
| We design for inclusion | Digital improvement must preserve assisted support, accessibility and language access |
| We bring compliance in early | Privacy, records, security and data governance should not be left to the end |
| We challenge respectfully | The team should challenge channel-first or technology-first solutions where they do not serve the full journey |
| We protect focus | Not every channel-related request becomes a Channel Strategy Y2 deliverable |

## Artefact standards

Channel Strategy Y2 artefacts should be practical, lightweight and easy for other teams to use.

| Standard | Description |
| --- | --- |
| Plain English | Avoid jargon unless needed; explain terms clearly |
| Reusable | Create patterns that can apply to multiple services |
| Decision-ready | Make recommendations and trade-offs visible |
| Evidence-informed | Use demand, customer effort, repeat contact, staff insight and feasibility evidence |
| Accessible | Consider WCAG 2.2 AA, plain language and assisted pathways |
| Compliance-aware | Identify privacy, records, security and data implications |
| Versioned | Show status, owner and last updated date |
| Actionable | Include next steps, owners or decision points |

### Prioritisation rules

Prioritise work that:

1. supports a Y2 value drop
2. affects a high-demand or high-effort journey
3. creates a reusable pattern
4. reduces repeat contact or channel switching
5. improves handover, knowledge or status clarity
6. protects accessibility, equity or trust
7. prevents rework in another active initiative

Deprioritise work that:

1. is a one-off channel preference
2. has no clear owner
3. requires major delivery effort without sponsor support
4. duplicates another project
5. does not support connected interactions
6. can wait until a reusable pattern is available

## Summary

The Channel Strategy Y2 way of working is designed to maximise influence without creating unnecessary delivery burden.

The project team should provide enough structure to align related work, enough challenge to prevent channel-by-channel optimisation, and enough practical support to help teams apply the framework.

The preferred stance is:

**advise where light input is enough, collaborate where the work shapes the framework, enable where the pattern can be reused, and oversee where alignment matters but delivery sits elsewhere.**
